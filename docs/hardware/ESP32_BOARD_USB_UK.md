# ESP32-S3 N16R8: фото плати та передумови USB Host

Дата: 2026-10-26. Фотографії власника:
[лицьова сторона](photos/esp32_s3_front_20261026.png),
[зворотна сторона](photos/esp32_s3_back_20261026.png).

## Видиме на фото

- Маркування екрана: `ESP32-S3-N16R8`, `N16R8`. Повне позначення WROOM-1
  на фото не підтверджене; попередню згадку в коментарі чату уточнено.
- Два USB-C, позначення COM/USB і два майданчики USB-OTG на звороті.
- Layout схожий на DevKitC-compatible; точні виробник/ревізія та схема невідомі.
  Зовнішня схожість не ідентифікує оригінальну Espressif DevKitC-1.
- Пізніше ROM probe підтвердив ESP32-S3 rev. 0.2 і Flash 16 MB; чип повідомляє
  embedded PSRAM 8 MB. Це не перевірка цілісності RAM. Наша firmware ще не запускалась.

Read-only зчитування: [esp32_chip_probe_v1.json](esp32_chip_probe_v1.json).
CH343 USB-UART визначився як COM14. esptool 5.6.0 працював із ROM без stub;
Flash/eFuse не записувалися, після операції виконано hard reset. Поточну
прошивку цим кроком не зберігали й не замінювали. Інструмент установлено лише
в ізольоване `.venv-esp32`; основне середовище моделі не змінене.

## Кандидат підключення

COM — кандидат для прошивання/журналу через USB-UART; USB — кандидат native
USB Host для GPW70 receiver. На ESP32-S3 native USB D−=GPIO19, D+=GPIO20 за
[офіційним ESP-IDF USB README](https://github.com/espressif/esp-idf/blob/master/examples/peripherals/usb/README.md).
Ці GPIO не призначаємо сенсорам. Routing конкретної плати ще потрібно перевірити;
наявні сенсорні підключення з фотографії повністю не відновлюємо навмання.

Для R8 variants з Octal PSRAM офіційний
[DevKitC guide](https://documentation.espressif.com/esp-dev-kits/en/latest/esp32s3/esp32-s3-devkitc-1/user_guide_v1.1.html)
також резервує GPIO35/36/37 під пам'ять. Не закладаємо їх у sensor pinout
до перевірки фактичного module/memory profile.

У [bench-проєкті автора](https://github.com/maxgerhardt/esp32s3-usb-host-keyboard)
для схожої N16R8 devboard USB-OTG solder jumper подає живлення з COM до USB.
Це орієнтир, не доведена схема нашої плати. За фото не можна гарантувати стан
перемички, VBUS, захист від зворотного живлення чи допустимий струм receiver.
Власник має мультиметр. Уточнення 2026-10-27: підключати щупи вміє;
потрібні конкретні режим вимірювання й точки, а не фото приладу для вибору гнізд.

## Підключення і наступне вимірювання, 2026-10-27

Отримано [актуальне фото](photos/esp32_receiver_connection_20261027.jpg):
обидва USB-C плати зайняті; білий кабель іде за межі кадру, чорний через
кабель/перехідник до receiver. Маркування портів/тип усіх з'єднань і наявність
data lines за цим фото не встановлені. USB receiver досі не виявлено firmware.

Наступний запропонований тест — **постійна напруга V⎓**, діапазон 20 V
або automatic DC. COM живить ESP від ноутбука. Чорний щуп на позначений GND
плати; червоний по черзі на кожний із двох майданчиків біля напису USB-OTG
на звороті. Записати обидва значення; не торкатися одночасно двох точок
одним щупом. Це перевірка потенціалів у можливій ділянці USB power path,
не підтвердження VBUS безпосередньо на контактах receiver. Призначення
майданчиків і routing clone board остаточно не встановлені.
Власник повідомив результат V⎓ відносно GND: перший майданчик **4.84 V**,
другий **0.15 V**, різниця **4.69 V**. Порядок — порядок вимірювання власника,
а не встановлені left/right або назви nets. Це апаратне вимірювання,
повідомлене власником, не симуляція й не автоматичний запис мультиметра.
Між майданчиками немає низькоомного з'єднання за цього стану живлення;
висновок про розімкнений USB power jumper добре узгоджується з результатом.
Це ще не прямий вимір VBUS на receiver.

Додатково звірено [первинний bench-опис автора](https://community.platformio.org/t/esp32-s3-as-usb-host-with-tinyusb/52691):
на його DevKitC N16R8 USB-OTG jumper обходить diode та з'єднує живлення COM
із native USB VBUS. Автор посилається на
[схему YD-ESP32-S3 V1.4](https://github.com/vcc-gnd/YD-ESP32-S3/blob/main/5-public-YD-ESP32-S3-Hardware%20info/YD-ESP32-S3-SCH-V1.4.pdf).
Це підтверджує функцію в спорідненій схемі, не встановлює виробника/ревізію
саме нашої clone board. Пряме з'єднання живлення також прибирає ізоляцію портів:
після такого bridge native USB не підключається до іншого джерела живлення/PC.

Наступна запропонована перевірка перед зміною jumper: повністю від'єднати
від ESP обидва USB та будь-які інші джерела/модулі, дочекатися згасання LED,
вибрати Ω. Чорний щуп на GND, червоний на майданчик, де було 0.15 V.
Записати початковий та усталений опір (почекати кілька секунд): стабільний
майже нульовий опір потребуватиме додаткового з'ясування перед з'єднанням
майданчиків. Власник повідомив: немає прозвонки, показ опору плавно зростає
до самотньої `1`, зокрема на 2000K. Точна модель мультиметра невідома
(придбаний в «Аврорі»). Ймовірний overload indicator після заряджання
ємності; це не слід записувати як 1 Ω або точний вимір >2 MΩ без звірки
приладу/контакту. За описом стійкого низького опору не спостерігалося.
Jumper не змінено. Після переходу на два наземні peer USB Host/перемичка
на ESP більше не є передумовою обраної схеми; подальше паяння/вимірювання
цієї гілки зупинено: [поточна архітектура](GROUND_LINK_ARCHITECTURE_UK.md).
Прозвонка/Ω нижче — окремий тест лише на повністю знеструмленій платі.

## Відкладена перевірка: перемичка без живлення

Власник уточнив, що приймач має працювати без ноутбука безпосередньо через ESP.
Перевірка нижче потрібна для з'ясування живлення USB Host, а не для роботи
геймпада в ноутбуці. Після пояснення призначення вимірювання зупинено;
користувач ще не повідомив жодного результату. Поточні підключення не змінювалися.

1. Повністю від'єднати ESP від USB, FC, сенсорних модулів та джерел живлення.
2. На мультиметрі чорний провід — у COM, червоний — у гніздо з позначенням V/Ω
   (воно може бути спільним VΩmA), не в окреме A/10A. Увімкнути прозвонку зі звуком.
   На невідомій моделі положення перемикача не вгадувати; за потреби попросити фото.
3. Торкнутися щупами один одного: стабільний писк і близьке до нуля значення
   підтверджують режим/контакт щупів.
4. По одному щупу на кожний із двох прямокутних майданчиків USB-OTG на звороті.
   Контакти всередині USB-C для цього не чіпати.
5. Записати Ω і наявність **сталого** писку. Стабільні приблизно 0–1 Ω вказують
   на пряме з'єднання; OL/немає сигналу не підтверджує його. Короткий писк від
   заряджання конденсаторів не прирівнювати до замкненої перемички.

Це не перевірка VBUS. Після результату треба окремо перевірити живлення
приймача в обраній схемі через доступні безпечні точки вимірювання.
Не даємо команду замкнути USB-OTG за одним фото або 5V на header: це не доводить
напругу на USB-порту чи сумісність джерел живлення.

Оновлення стенду: [USB_PROBE_FIRMWARE_UK.md](USB_PROBE_FIRMWARE_UK.md).
Повну попередню Flash збережено й звірено; USB-діагностику записано через COM14.
Native USB Host library успішно стартувала, за 12 s немає panic/reset.
При першому boot log receiver ще не підключений, за уточненням власника.
Спочатку перевіряємо звичайне підключення пасивного receiver, COM — єдине
живлення ESP. Відсутність enumeration після підключення вимагатиме перевірки
VBUS; не трактуємо `device=0` порожнього порту як несправність.

Перевірено: фото, документація, ROM UART chip/Flash probe, backup/flash і USB Host startup;
раніше Windows XInput GPW70.
2026-10-27 після повідомлення про підключення receiver: без reset і після reset
ESP працює, але `device=0 reports=0`. Це не підтверджує стан VBUS або точність
підключення. Збережено [фізичне спостереження](esp32_usb_attached_20261027_v1.json).
Актуальне фото підключення отримано; власник знає підключення щупів.
Виміряно 4.84/0.15 V на USB-OTG pads; перевірка опору до GND ще очікується.
Не перевірено: jumper continuity, VBUS, USB enumeration/пакети GPW70 на ESP,
radio loss, firmware timing та вихід FC. Хостові 866 tests не підтверджують
ці апаратні властивості. Контракти моделі й lease незмінні.
