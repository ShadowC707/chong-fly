# Betaflight SITL + PyBullet: синхронізація і відповідність газу

Продовження: [нейронні прогони та виявлена несумісність RC-одиниць](SITL_NEURAL_INTEGRATION_UK.md).
Нижче — результати початкових 20 коротких прогонів; вони не покривають сильні повороти.

## Результат та межа висновку

Завершено обмежений дослід без апаратури, мережі та кімнат: **20/20 прогонів
по 4 с**, зі справжнім кодом Betaflight PID/ANGLE/mixer та окремо зміненим
механізмом часу й обміну даними у host-збірці SITL.

Повні масиви стану, motor outputs і RC команд збігаються точно між повторами,
включно зі штучними паузами комп'ютера. Знаки Roll/Pitch/Yaw правильні.
Стабільність цього стенду тепер дозволяє перейти до перевірки незмінної
політики. Це **не допуск до польоту** і не підтвердження точності моделі апарата.

Артефакти: `output/sitl_bringup_v1/lockstep_v1/`.

- `report.json`: вихідні результати, таблиця газу, хеші виконаної прошивки.
- `validation.json`: незалежний перерахунок перевірок зі збережених трас.
- `comparison.png`: висота, кути й команди газу.
- `r0_*`, `r1_*`, `r2_*`: 12 прогонів без утримання висоти.
- `alt0_*`, `alt1_*`: 8 прогонів з незмінним `AltitudeHold`.
- `trace.npz` у кожній папці: час, стан, PWM, моторні виходи, підтвердження кроків.
- `firmware.patch`: точний патч виконаної host-прошивки.
- `provenance.json`, `source_snapshot/`: знімок джерел для відтворення;
  зібраний після досліду, не атомарний маніфест на момент його початку.

## Що саме виправлено

Попередній асинхронний запуск мав 5 завершень із 8 спроб та відмінності
повторних траєкторій. Код SITL поєднував окремі потоки обміну, годинник,
похідний від реального часу, та синхронізацію видачі моторів. Цей дослід
замінює їх разом; він **не ізолює один-єдиний винний механізм**.

Новий host-стенд має один потік виконання і явні кроки:

1. Python надсилає стан тіла, RC, номер кадру та тривалість 4000 мкс.
2. Прошивка встановлює віртуальні сенсори й виконує scheduler з квантом 10 мкс.
3. Після повного інтервалу повертає номер кадру, свій час, кількість моторних
   оновлень та чотири виходи у native QUADX порядку.
4. PyBullet робить фізичний крок; новий стан використовується в наступному кадрі.

MSP/CLI обслуговуються тим самим потоком. Початок роботи позначено явним
`CHONG_LOCKSTEP_READY` після ініціалізації. Перед кожним прогоном перевірено
штатний дозвіл ARM і режим ANGLE; failsafe не вимикався для обходу readiness.

RC оновлюється кожні 20 мс; проміжні кадри не позначають стару команду як
новий RX frame. Час `micros` і `millis` походить з одного лічильника.
Дублікат останнього ідентичного запиту повертає кешовану відповідь без нового
кроку. Змінений дублікат і пропуск номера відхиляються без руху годинника.
Це перевірено на виконаній прошивці, не лише в Python-тестах.

Приватний протокол `CFS1` працює тільки між процесами ізольованого Linux
контейнера на localhost. Це **не протокол ESP32, MSP чи реального G4**.

## Чого патч не доводить

Математику PID, ANGLE, mixer, rate curves та failsafe не переписано. Але це
**модифікований SITL**, а не виконання незмінного upstream у реальному часі:

- `sitl.c`: інший годинник, потік обміну, RX freshness, моторні підтвердження.
- `main.c`: запуск host-циклу.
- `scheduler.c`: усунення busy-wait до майбутнього дедлайну при замороженому часі.
- CPU-вартість firmware tasks ідеалізована як нульова; навантаження G4 не відтворено.
- На 4 мс фізики припадає **32 моторні оновлення**. Стан сенсорів всередині
  цього інтервалу утримується, а фізика використовує останній motor output.
  Це не 32 окремі фізичні підкроки і не усереднення тяги.
- Збіжність при зменшенні фізичного кроку тут не перевірялася; швидкі коливання
  та граничну стійкість регулятора з цих дослідів оцінювати не можна.
- Справжній IMU/AHRS, затримки сенсорів, transport watchdog і реальна тяга
  не є предметом цих 20 прогонів.

Отже, ми усунули залежність **цього визначеного обчислювального досліду** від
швидкості ноутбука. Ми не довели еквівалентність фізичному G4.

## Таблиця газу і утримання висоти

На нерухомому віртуальному апараті, після штатного ARM, виміряно:

| RC throttle | Нормований motor output, приблизно |
|---:|---:|
| 1150 | 0.154 |
| 1180 | 0.183 |
| 1200 | 0.203 |
| 1210 | 0.213 |
| 1220 | 0.223 |
| 1250 | 0.253 |
| 1300 | 0.303 |

У стенді прийнято `RPM = motor_output × max_rpm`, а тягу — пропорційною
`RPM²`. Це задане, **ще не відкаліброване на моторах** припущення.
Для поточних маси, коефіцієнта тяги та max RPM потрібне значення
`motor_output = 0.21341575`. Інверсія виміряної таблиці дає **1210.4157 RC**.
Окремо перевірено сусідні цілі значення 1210 та 1211.

Старе `1213.41575` є значенням у прямому reference RPM-просторі старої моделі;
передавати його без перетворення у RC Betaflight некоректно. Водночас навіть
найближче ціле `1210` не забезпечує точну рівновагу: модель повільно знижується.

Для контрольного замкненого контуру залишено незмінним `AltitudeHold` і його
коефіцієнти. Перетворення виконується лише на виході:

`AltitudeHold reference PWM → (PWM − 1000)/1000 → inverse measured map → integer RC`.

Жодної екстраполяції за виміряний діапазон: вихід за межі зупиняє дослід.
Вхід висоти — ідеальна дальність до рівної підлоги з відповідними поточними
кутами й геометричним зсувом датчика, 50 Гц. Це **не** попередній held-сенсор
15 Гц і не доказ роботи з реальним VL53L0X.

## Зафіксований протокол і числа

Чотири випадки: hover, Roll, Pitch, Yaw. Для трьох маневрів подано `+50 RC`
між 1.0 та 1.5 с, потім нейтраль. Фізика 250 Гц, RC 50 Гц, горизонт 4 с.
Початкові двигуни мають рівноважні RPM; це не тест зльоту.

Для фіксованого газу зроблено три повтори кожного випадку; у третьому додано
30 мс wall-time паузи кожні 125 фізичних кроків. Для AltitudeHold — два повтори,
другий з такими самими паузами. Параметри не підбиралися між прогонами.

| Маневр | Макс. похибка висоти, газ 1210 | З AltitudeHold і таблицею |
|---|---:|---:|
| Hover | 27.231 см | 0.149 см |
| Roll | 22.721 см | 0.129 см |
| Pitch | 22.897 см | 0.138 см |
| Yaw | 11.835 см | 1.350 см |

Це максимальні абсолютні відхилення від 1 м за 4 с. Маленькі похибки праворуч
очікувані для ідеального датчика і відомої actuator map; вони не є прогнозом
точності справжнього дрона. Під час Yaw висота реагує сильніше, хоча кути
Roll/Pitch малі: однаковий середній RPM не означає однакову суму квадратів RPM.
Тут не проводилась окрема причинна абляція моторного мікшування.

Перевірки зі збережених трас:

- 20/20 завершили 4 секунди з ARM/ANGLE; усі дані скінченні.
- 1000 фізичних кроків у кожному прогоні; годинник firmware додав 4 000 000 мкс.
- Немає пропущених номерів підтверджень; приріст часу завжди 4000 мкс.
- 32 моторні оновлення в кожному фізичному інтервалі.
- Команди утримані протягом п'яти кроків; позитивні Roll/Pitch/Yaw дають
  відповідно рух праворуч / уперед / поворот за годинниковою стрілкою.
- Повторні `state`, `motors`, `pwm`, `time_s` збігаються через `np.array_equal`.
  Wall-time latency навмисно не порівнюється на рівність.
- 29 цільових тестів контрактів, контролера висоти та перевірки трас пройдено.

Старі 5/8 та нові 20/20 — різні серії й різні host-механізми, а не оцінка
ймовірності відмови з контрольованого статистичного експерименту.

## Файли та відтворення

Нові реалізації:

- `scripts/sitl/{Dockerfile.lockstep,patch_lockstep.py,lockstep.c}` — окрема збірка.
- `simulation/sitl_lockstep.py` — формат кадру, перевірка ACK, інверсія таблиці.
- `evaluate/sitl_lockstep.py` — підготовка, static map, 20 фізичних прогонів.
- `evaluate/report_sitl_lockstep.py` — перерахунок результатів і графік без Docker.
- `tests/test_sitl_lockstep.py` — контракти та негативні перевірки журналу.

Використано Betaflight commit `79065c96ba0bb5cdc675e67d7093e05dab8b330e`,
Linux Python 3.12, NumPy 2.2.6, PyBullet 3.2.7 з базового image попереднього
досліду. Windows PyBullet 3.25 з раннього rigid-body порівняння тут не виконувався.

SHA-256 виконаної прошивки:
`b9b857a30179de4464acb63ccae8e497dc1349bea9699c947d8e2677b9acedbc`.

SHA-256 точного firmware patch:
`580d4a2fa8bc6af00ab02d4d04bad1cf5796d150ecccae79cd92b054172ce7a0`.

Для нової серії потрібен запущений Docker Desktop і базовий image з
[попереднього звіту](SITL_BRINGUP_UK.md). Робоче середовище проєкту не замінюється.
Папка результатів повинна бути новою; запуск не перезаписує старий EEPROM.

```powershell
docker build --progress plain -f scripts/sitl/Dockerfile.lockstep -t chong-fly-sitl:lockstep-v1 scripts/sitl
$repoPath=(Get-Location).Path
$resultsPath=(Resolve-Path output/sitl_bringup_v1).Path
docker run --rm --network none --cpus 4 --memory 2g --mount "type=bind,source=$repoPath,target=/work,readonly" --mount "type=bind,source=$resultsPath,target=/results" chong-fly-sitl:lockstep-v1 python -u -m evaluate.sitl_lockstep --out /results/lockstep_repeat
.\venv\Scripts\python.exe -m evaluate.report_sitl_lockstep --root output/sitl_bringup_v1/lockstep_repeat
```

Для читання вже отриманих результатів Docker не потрібен:

```powershell
.\venv\Scripts\python.exe -m evaluate.report_sitl_lockstep
.\venv\Scripts\python.exe -m pytest tests/test_sitl_lockstep.py tests/test_sitl_contract.py tests/test_ready_sim_contract.py tests/test_altitude_control.py -q -p no:cacheprovider --basetemp .test-tmp-sitl-lockstep
```

Під час фінального оформлення Docker daemon уже був недоступний. Повторно
контейнери не запускалися: валідація виконана за збереженими повними трасами.
Digest збірки збережено з build log; це не повторне опитування image registry.

## Наступний крок

Підключити **незмінну мережу й координатор** до цього стенду через існуючий
сенсорний контракт. Почати з кількох зафіксованих простих сцен та відкрито
заданих сенсорних припущень; порівняти з попереднім симулятором. Це наступний
окремий експеримент, а не вже отриманий результат.

До оцінки швидких реакцій слід перевірити чутливість до фізичного кроку.
Потім додавати затримки/шум сенсорів та параметричну невизначеність. Зміни
ваг, навчання й PID не потрібні для першого такого порівняння. Реальний дрон
не потрібен для цих програмних перевірок; виміри апаратури знадобляться для
обґрунтованої калібровки, а не для самого запуску.
