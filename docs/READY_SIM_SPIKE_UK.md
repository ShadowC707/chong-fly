# Готовий симулятор: перевірка здійсненності

Дата: 2026-11-07. Статус: **нативна фізика запущена; Betaflight SITL лише
перевірено за вихідним кодом, не зібрано й не запущено**.

## Рішення за результатами

Готовий фізичний рушій можна додати як другий стенд без перебудови мережі,
координатора, ESP32-контракту чи основного симулятора. Перша реалізація на
`gym-pybullet-drones / PyBullet` працює у Windows в окремому середовищі.

У чотирьох простих маневрах з однаковими параметрами максимальна розбіжність
положення між наявною фізикою та Bullet становить 1.776 мм, орієнтації —
0.000330°. Це позитивна перевірка нашого інтегрування й адаптера сил/осей
на цих маневрах. **Це не доказ правдивості параметрів апарата або точності
нашого польотного регулятора:** обидва стенди навмисно використовують ті самі
параметри та той самий спрощений PID.

Тому зараз немає підстав переписувати весь симулятор. Наступна змістовна
незалежна перевірка — замінити спрощений PID на виконання відповідної версії
Betaflight у SITL. Мережу під результати цього досліду не перенавчали.

## Що саме зроблено

1. Створено окреме `.venv-ready-sim`, не змінюючи робоче `venv`.
2. Завантажено незмінений `gym-pybullet-drones`, commit
   `348b5c18a4bb770a48928b9d044decf77ca33302`, у локальну ігноровану папку
   `scratch/ready_sim/gym-pybullet-drones`.
3. Запущено початкову штатну модель CF2X на постійних hover RPM: 10 с,
   кінцева позиція `[0, 0, 1]`. Це лише перевірка запуску та рівноваги,
   не перевірка контролера і не модель нашого дрона.
4. Додано mesh-free URDF із параметрами нашої поточної моделі та явним
   відображенням моторів. Після цього виконано 4 парні досліди по 8 с:
   **8 прогонів, 64 с модельного часу**.
5. Збережено часові траси, JSON, графіки, контрольні суми, точний список
   пакетів окремого Windows-середовища та перевірено формат RC-пакета SITL.

## Контрольований протокол

Команди зафіксовано до запуску. Час фізики і внутрішнього PID — 4 мс;
RC-команда утримується 5 кроків, тобто оновлюється на 50 Гц.

| Дослід | Команди |
|---|---|
| hover | Нейтраль R/P/Y, постійний розрахунковий hover throttle |
| yaw_right | Yaw = 1640 від 1 до 2 с, потім 1500 |
| pitch_brake | Pitch = 1550 від 1 до 2 с, 1450 від 2 до 3 с, потім 1500 |
| roll_brake | Roll = 1550 від 1 до 2 с, 1450 від 2 до 3 с, потім 1500 |

Початок: позиція `(0,0,1)`, нульові швидкості й кути, мотори вже на
розрахункових hover RPM. Початкове збурення навмисно відсутнє.
Hover throttle = **1213.415751 PWM**. Це розрахункове значення моделі,
не калібрування справжньої силової установки.

Маса 0.13 кг, інерція, коефіцієнти RPM², моторна стала 25 мс, опір і
PID взяті без підбору з попереднього nominal manifest. Отримане співвідношення
максимальної тяги до ваги ≈21.96 успадковане з моделі й **не підтверджене
вимірюванням**. Нахил ±35° та Yaw ±200°/с також залишено для парності;
це не налаштування реальної плати з `angle_limit=60` та ACTUAL rates.

У PyBullet вимкнено його власне додаткове демпфування; явно прикладено
ті самі квадратичний опір поступальному руху та лінійний опір обертанню.
Затримка моторів також однакова. Сили й моменти чотирьох моторів обчислює
upstream; рух твердого тіла інтегрує Bullet. Наш код передає моторні RPM,
не підставляє бажану траєкторію чи орієнтацію.

Для FLU-системи координат додатна RC-команда Yaw означає від'ємну кутову
швидкість навколо Z. Перестановка моторів `[0,1,3,2]` тут стосується **нашого
генерованого URDF**, а не універсальної розводки G4 або штатного CF2X.
Кутову швидкість Bullet у світових координатах перетворено в body frame
перед подачею у PID.

## Виміряні результати

| Дослід | Максимальна різниця положення, мм | Максимальна різниця кута, град |
|---|---:|---:|
| hover | 0.00863 | 0 |
| yaw_right | 0.00692 | 0.0003291 |
| pitch_brake | 1.77536 | 0.00000307 |
| roll_brake | 1.77537 | 0.00000338 |

Усі траси мають скінченні значення. Обидва backend повертаються праворуч
приблизно на 56°. Початковий додатний Pitch рухає апарат уздовж +X,
додатний Roll — уздовж −Y; протилежні імпульси гальмують і потім спричиняють
відкат. Це задана тестова послідовність, не реалізація STOP.

У цьому досліді **немає AltitudeHold**: при Yaw обидва backend набирають
близько 38.87 см, при Roll/Pitch втрачають близько 9.82 см за 8 с.
Ці числа не слід переносити на попередні прогони з висотним контуром.
За сталого колективного RPM симетричне додавання/віднімання RPM для повороту
збільшує суму квадратів RPM, отже сумарну тягу; нахил зменшує її вертикальну
складову. Обидва рушії успадковують цю саму модель мікшера й тяги.

циліндр радіуса 0.2 м, а не сфера з demo; колізійне зіставлення не проводилося.

## Чому готовий Betaflight-приклад не можна прийняти без адаптації

Перевірено upstream `BetaAviary.py` і `clone_bfs.sh` на наведеному commit,
а також вихідний код Betaflight commit
`79065c96ba0bb5cdc675e67d7093e05dab8b330e`, що відповідає короткому hash
збереженого dump G4. Це перевірка коду, не фактичного поточного стану плати.

- Upstream скрипт збирає старий Betaflight `cafe727`, патчить старі шляхи
  `src/main/target/SITL` і підкладає власний `eeprom.bin`. У версії нашого
  dump SITL знаходиться в `src/platform/SIMULATOR`. Автоматично копіювати
  стару конфігурацію чи переносити повний апаратний dump у SITL не можна.
- `BetaAviary` приймає thrust/body rates (CTBR). Це відрізняється від наших
  RC-команд із кутовим Roll/Pitch у ANGLE. Потрібен явний RC/ANGLE шлях.
- Upstream передає quaternion identity й нульові прискорення, швидкості та
  позицію в FDM-пакеті. У перевіреному target `USE_IMU_CALC` вимкнено, тому
  орієнтація задається симулятором. Такий приклад не доводить правильність
  ANGLE або оцінювання орієнтації. Спершу потрібна коректна передача орієнтації;
  окремий IMU/AHRS-дослід можливий після узгодження прискорень та осей.
- Upstream автоматично задає AUX arming; наш codec не відкриває сокетів і
  вимагає явно передати всі AUX-канали. Віртуальне arming і режими треба
  описати в окремій конфігурації SITL.
- Формат RC у перевіреній версії: timestamp double + 16 uint16,
  A/E/T/R і AUX, 40 байтів на Linux x86-64 little-endian. Це **не** протокол
  обміну з ESP32. FDM — окремий пакет; його production-адаптер ще не написано.

## Як повторити у Windows

Поточний окремий стенд уже встановлено. З кореня проєкту:

```powershell
.\venv\Scripts\python.exe -m evaluate.ready_sim_spike --backend legacy
$env:PATH="$(Resolve-Path .venv-ready-sim)\Library\bin;$env:PATH"
$env:PYTHONPATH=(Resolve-Path scratch/ready_sim/gym-pybullet-drones).Path
.\.venv-ready-sim\python.exe -m evaluate.ready_sim_spike --backend pybullet
.\.venv-ready-sim\python.exe -m evaluate.ready_sim_spike --backend compare
.\venv\Scripts\python.exe -m pytest tests/test_ready_sim_contract.py -q -p no:cacheprovider --basetemp .test-tmp-ready-sim
```

Для нового комп'ютера з conda, перед цими командами:

```powershell
conda create --prefix .venv-ready-sim --file configs/ready_sim_win64_explicit.txt --yes
git clone https://github.com/learnsyslab/gym-pybullet-drones.git scratch/ready_sim/gym-pybullet-drones
git -C scratch/ready_sim/gym-pybullet-drones checkout 348b5c18a4bb770a48928b9d044decf77ca33302
```

Це Windows lock, не переноситься прямо на Linux. Використані Python 3.12.16,
conda PyBullet **3.25** (не плутати з PyPI 3.2.7), NumPy 2.5.4.
Повний пакет залежностей upstream для RL не встановлювався; перевірено
саме `CtrlAviary/Physics.PYB`, не всі приклади чи повний upstream test suite.
Вихідний upstream checkout залишено чистим.

## Межа цього етапу й наступна робота

На цьому комп'ютері знайдено лише зупинений WSL `docker-desktop`, без
Ubuntu; Docker daemon не працює, Linux toolchain для SITL не готовий.
Не встановлювали нову ОС, не запускали Docker, не прошивали G4.
Це причина, чому **SITL ще не перевірений виконанням**, а не падіння його збірки.

Наступний обмежений етап:

1. Підготувати Linux-середовище та зібрати зафіксований Betaflight SITL.
2. Задати явну віртуальну конфігурацію ANGLE, rates, AETR, AUX та mixer;
   не переносити апаратні UART/pin/resource налаштування. Уточнити поточний
   dump G4, якщо він змінився.
3. Реалізувати FDM/RC/motor adapter: час, quaternion, осі gyro/accel, одиниці,
   індекси моторів, відповідність виходу моторів RPM/тяги. Жодна перестановка
   чи формула зі старого прикладу не приймається без перевірки.
4. Спершу повторити hover і окремі RC-імпульси з реальним firmware loop.
   Лише після перевірки напрямків і масштабів підключати незмінну мережу,
   сенсори та кімнати. Це дасть нову інформацію, а не просто іншу картинку.

Фізично зібраний дрон для цього програмного етапу не потрібен. Вимірювання
реальних сенсорів, маси, моторів і налаштувань усе одно потрібні для
обґрунтування sim2real: готовий рушій не визначає їх замість нас.
