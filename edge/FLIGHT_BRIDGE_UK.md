# FlightBridge v1: контракт передачі керування

Нова обгортка над FlightRuntime: `edge/flight_bridge.py`. Канонічний артефакт
з модулем: `data/edge/k306_tau025_bridge_v1`. Ваги та AltitudeHold збережені.
Новий експортер включає bridge у контрольні суми; loader приймає також старі
пакети без bridge. Старі пакети не перезаписані.

## Межі версії

Це програмний контракт і еталон watchdog, не прошивка ESP32 чи UART-драйвер.
CommandGate має виконуватись на стороні приймача незалежно від процесу Pi.
Модуль не армує двигуни та не визначає фізичну дію при втраті всіх джерел
керування. Її потрібно погодити й реалізувати в апаратному арбітрі до польоту.
Повернення MANUAL означає відкликання права Pi, а не гарантію наявності пульта.

Перший MVP підтримує лише вхід зі стабілізованого зависання поблизу 1 м.
Не реалізує захоплення довільної висоти або безшовний вхід на швидкості.
Параметри — консервативні початкові умови перевірки, не льотні нормативи.

## Стани та повноваження

| Запит / стан | Поведінка | Команда для застосування |
|---|---|---|
| MANUAL | Негайне відкликання AUTO, сенсори не потрібні | None |
| SHADOW | Оновлює мережу та контролери на свіжих даних | None; preview лише для діагностики |
| AUTO до готовності | Залишається SHADOW | None |
| AUTO після готовності | Видає обмежену в часі lease | PWM + sensor sequence + TTL |
| FAULT | Блокує автономні команди | None |

Запит AUTO має надходити від зовнішнього дозволу оператора/арбітра кожен крок.
SHADOW не має повноважень. MANUAL має пріоритет над помилками телеметрії.
FAULT скидається тільки явно через reset_fault() у MANUAL; потім потрібен
новий період SHADOW. Повторного автоматичного захоплення після FAULT немає.

## Умови входу в AUTO

Усі умови мають виконуватись безперервно 0.5 с:

- Свіжі кадри кожні 10–30 мс, вік ≤40 мс, зростаючі sequence та timestamp.
- Спільний синхронізований snapshot navigation/altitude у монотонному часі Pi.
- Штатна валідація AltitudeHold: valid, дальність, нахил, вік, стрибки висоти.
- Висота 1±0.10 м, оцінена вертикальна швидкість ≤0.10 м/с, нахил ≤0.15 рад.
- Норма нормованого потоку після фільтра tau=0.12 с ≤0.015. При висоті 1 м
  це приблизно 0.06 м/с за контрактом симулятора; це не вимірювання true speed.
- Мінімум передньої ToF ≥0.95 м.
- Різниця розрахованої команди та свіжої застосованої ручної команди:
  throttle ≤15 PWM, Roll/Pitch ≤35 PWM, Yaw ≤20 PWM.

manual_pwm — остання фактично застосована ручна команда із цього ж свіжого
snapshot, а не положення джойстика невідомого віку. Адаптер має це забезпечити.

Перша команда AUTO точно копіює manual_pwm. Наступні команди мають обмеження
швидкості зміни: throttle 150, Roll/Pitch 2000, Yaw 10000 PWM/с. Це явна
модифікація застосованих команд обгорткою; нейронна модель не змінена.
Потрібно перевірити її на інтеграційному стенді: вона не успадковує автоматично
всі результати серій без bridge. Умови зависання обмежують лише вхід, не
забороняють нормальний крейсерський рух після передачі керування.

## Невалідні дані

Пропущений, прострочений, дубльований, несинхронізований або невалідний кадр
переводить bridge у FAULT. Очікувані помилки даних перетворюються на явний
статус без виходу винятку до циклу адаптера. Помилки програмування потребують
зовнішнього supervisor; незалежний receiver watchdog покриває мовчання Pi.

Grace/replay попередньої команди не реалізований. Runtime може частково
оновити нейронний стан перед помилкою altitude; тому після помилки весь
стан скидається перед повторним SHADOW, продовжувати з нього не дозволено.

## Контракт приймача (ESP32)

CommandLease.sequence повторює номер сенсорного кадру ESP. Gate приймає лише
відповідь на останній надісланий кадр з новим sequence та чинним зовнішнім AUTO.
TTL ≤40 мс від часу відправлення сенсорного кадру за годинником ESP,
**не від часу отримання запізнілої відповіді**. Тому буфер UART не подовжує
життя старих команд. sensor_sent_s треба брати з локального запису ESP,
не довіряти повернутому Pi часу. Годинники Pi й ESP для цього watchdog
не потрібно порівнювати; адаптер окремо узгоджує час сенсорів для Pi.

Expiry, replay, втрата AUTO або регресія часу відкликають команду та фіксують
tripped. Нові пакети не поновлюють керування самі: потрібен explicit reset
при відкликаному AUTO. Номери кадрів не скидаються. Перезапуск ESP/Pi та
новий сеанс каналу потребують явного узгодження/очищення черг у майбутньому
транспортному адаптері. CRC, формат UART і session handshake ще не реалізовані.

Виклик command(now_s=..., auto_authorized=...) має відбуватись у кожному
циклі ESP, навіть коли нових повідомлень немає. При None арбітр виконує свою
заздалегідь визначену дію; продовження старої RC-команди не дозволене контрактом.

## Перевірки

`tests/test_flight_bridge.py`: готовність/прогрів, відмова входу при русі,
негайний MANUAL, дубльовані/застарілі кадри, порушення строків, latched fault,
обмеження першої команди/газу, незалежне expiry, replay і запізнілий UART.
Використано fake-runtime для керування умовами та справжній NumPy runtime
із маленьким синтетичним експортом для перевірки fault.

`evaluate/validate_flight_bridge.py`: чотири фізичні прогони по 4 с зі справжнім
k306, 50 Гц bridge / 250 Гц standalone, seed=20261021:

- Hover 1 м: вхід на 0.50 с, швидкість у момент входу 0 м/с.
- Початкова швидкість 0.6 м/с: вхід протягом вікна запиту AUTO заборонений.
- Висота 1.4 м: вхід заборонений.
- Невалідний нижній відлік на 2.0 с: негайний FAULT, без автономної команди.
- У всіх сценаріях MANUAL з 3.0 с негайно припиняє видачу lease.

Поле faults у physical.json рахує **кадри у FAULT**, не число незалежних
відмов. Для dropout 50 кадрів є наслідком однієї ін'єкції.
Ручний контур у цих симуляціях — окремий AltitudeHold для підтримання
умов експерименту, а не реалізація апаратного fallback.

```powershell
.\venv\Scripts\python.exe -m evaluate.validate_flight_bridge --out data/diagnostics/flight_bridge_repeat/physical.json
```

Далі потрібні реальні результати benchmark на Pi (спочатку на наявному 4B,
окремо на Zero 2W) і контракт/реалізація транспорту та ESP-арбітра на стенді.

Підсумок виконаної перевірки: **719 passed in 42.34s**. Чотири фізичні
сценарії пройшли assertions. Артефакти: `data/diagnostics/flight_bridge_v1/physical.json`
та `parity.json`. Чисельна відповідність нового пакета PyTorch на 2000 кроках
і чотирьох конфігураціях pipeline: максимум помилки PWM 0.00012207,
розбіжностей причин втручання немає. Ця перевірка parity стосується
нейронної моделі та попереднього pipeline, не доводить фізичну безпечність bridge.
