# Chong-Fly: локальний демонстратор

## Як запустити два демо

Підсумок ітерації, з якого взято числа нижче: [docs/REITERATION_REPORT_UK.md](../docs/REITERATION_REPORT_UK.md).

### Демо 1 · Standalone (без Docker)

Потрібен Python 3.12. Один раз створіть середовище з кореня репозиторію (демо використовує лише numpy і torch із `requirements.txt`):

```powershell
python -m venv venv
.\venv\Scripts\python.exe -m pip install --upgrade pip
.\venv\Scripts\python.exe -m pip install -r requirements.txt
```

Запуск:

```powershell
.\venv\Scripts\python.exe -m demo
```

1. Відкрийте **http://127.0.0.1:8765/**.
2. У **Налаштуваннях сцени** оберіть профіль. За замовчуванням це **фазовий із бічним захистом і виходом із FAILED** (`phased_failed_exit`). Попередній основний профіль `phased_side_guard` лишається у списку для порівняння.
3. Для сцени залиште **«Кімната 8×8 · перешкоди»** і в полі **Розподіл** оберіть **«Скупчення та просвіти»** (clustered) або **«Рівномірно»** (uniform).
4. Залиште **«Автономне»** керування й натисніть **«Старт»**.
5. Щоб показ ішов швидше, у списку **«Темп»** оберіть **2×** або **4×**. Множник змінює лише кількість фіксованих кроків фізики за секунду реального часу. Крок фізики (dt) не змінюється, а ліміт кроків за одне опитування масштабується разом із множником. Тому траєкторія за того самого seed і старту побітово однакова при 1× і 4× (`tests/test_demo_speed.py`). Множник не прискорює обчислення: фактичний темп обмежений тим, скільки кроків комп'ютер встигає порахувати, а наздоганяння пакетами немає. На комп'ютері автора `phased_failed_exit` рахується максимум ≈1,26× реального часу (5 с польоту за 3,96 с), тож 2× і 4× там дають ≈1,25×. Для SITL множник недоступний, бо там темп задає lockstep із Betaflight.

Поруч зі сценою видно:
- **«Хто керує зараз»** — мережа, стадія конвеєра або фаза координатора;
- **«Частка мережі»** — частка тактів AUTO без STOP, де команда після координатора відрізняється від мережевої не більше ніж на 10 PWM (як у розділі 2 плану);
- **конус ToF 45°** на мапі (помаранчева дуга — найближче повернення ToF);
- **точки пам'яті загроз** — лише для профілів, які її мають (конвеєр v1 і r7). Їх показано в **оцінці контролера**: позиції з одометрії flow і курсу від точки старту, тобто там, де перешкоди «думає» бачити сам контролер. Порожнє кільце — оцінка контролером власної позиції; розходження з дроном показує накопичену похибку одометрії.

### Демо 2 · Betaflight SITL (Docker)

1. Запустіть **Docker Desktop** (Linux-контейнери). Потрібен локальний образ `chong-fly-sitl:neural-v1` (див. «Збирання SITL-образу» нижче). Без нього SITL-демо не запуститься.
2. З кореня репозиторію:

   ```powershell
   .\scripts\sitl\demo.ps1
   ```

3. Відкрийте **http://127.0.0.1:8765/** і в полі **Фізика наживо** оберіть **Betaflight SITL + PyBullet**.

SITL-демо літає лише з профілем **`phased_failed_exit`** (з кроку 9; раніше `phased_side_guard`) поверх Candidate A (`adaptive_tau`) при TWR 5. Дані профілю SITL лежать у репозиторії: `data/scenarios/reiteration_v1/sitl`, контрольні суми перевіряються. Конвеєр v1/r7 у SITL недоступний: йому потрібен сигнал курсу, якого контур SITL не дає. Тому v1 показуємо лише в Standalone. Темп SITL — приблизно 0,5× реального часу, тож для показу задайте **Тривалість 60 с** (політ триває ~2 хв).

#### Збирання SITL-образу

Вихідні коди двох зовнішніх проєктів у репозиторії не зберігаються. Точні версії, з яких зібрано перевірений образ:

| Проєкт | Репозиторій | Коміт |
|---|---|---|
| Betaflight | https://github.com/betaflight/betaflight | `79065c96ba0bb5cdc675e67d7093e05dab8b330e` (підмодуль `src/config`: `e37834762542f9b7087e917431a0141cbb04a4da`) |
| gym-pybullet-drones | https://github.com/learnsyslab/gym-pybullet-drones | `348b5c18a4bb770a48928b9d044decf77ca33302` |

```powershell
git clone https://github.com/betaflight/betaflight.git scratch/ready_sim/betaflight
git -C scratch/ready_sim/betaflight checkout 79065c96ba0bb5cdc675e67d7093e05dab8b330e
git clone https://github.com/learnsyslab/gym-pybullet-drones.git scratch/ready_sim/gym-pybullet-drones

docker build --progress plain -f scripts/sitl/Dockerfile -t chong-fly-sitl:79065c96b-v1 scratch/ready_sim
docker build --progress plain -f scripts/sitl/Dockerfile.lockstep -t chong-fly-sitl:lockstep-v1 scripts/sitl
docker build --progress plain -f scripts/sitl/Dockerfile.neural -t chong-fly-sitl:neural-v1 scripts/sitl
```

`Dockerfile` сам перевіряє коміт Betaflight і підтягує підмодуль `src/config`. Подробиці збирання: [SITL_BRINGUP_UK](../docs/SITL_BRINGUP_UK.md), [SITL_LOCKSTEP_UK](../docs/SITL_LOCKSTEP_UK.md), [SITL_NEURAL_INTEGRATION_UK](../docs/SITL_NEURAL_INTEGRATION_UK.md). Щоб перенести готовий образ на інший комп'ютер без збирання: `docker save chong-fly-sitl:neural-v1 -o chong-fly-sitl.tar`, а там `docker load -i chong-fly-sitl.tar`.

### Що показує кожен профіль

| Профіль | Що видно в демо | Де слабкий |
|---|---|---|
| **`phased_failed_exit`** (основний у Standalone і SITL, крок 9) | Те саме, що `phased_side_guard`, плюс вихід із застрягання. Якщо дрон 1 с нерухомо стоїть у **FAILED**, координатор запускає новий епізод гальмування й повороту: перший повтор продовжує попередній поворот, наступні змінюють напрям. Бюджет — 3 повтори, як у WAIT_CLEAR; відновлюється після 5 с чистого руху. Після вичерпання дрон лишається у FAILED з тим самим гасінням flow, а індикатор показує **«Утримання: повтори вичерпано — потрібен оператор»**. На 23 seed демо застрягання (частка FAILED) 20,2% → 13,7%, контакти 1/23 → 1/23, «безпека ✓» 13/23 → 16/23. На 20 прогонах розкиду FAILED не виникає, тож результати збігаються з `phased_side_guard` ([звіт кроку 9](../output/pipeline_v1_step9/report_uk.md)) | Поворот на місці не виводить дрон із тісного кута: повтори вичерпуються, і він стоїть в утриманні (seed 3934218795 з AUTO на 6 с, 20261025). Новий рух після виходу з FAILED може підвести ближче до іншої перешкоди: у divided_2026112012 мінімальний зазор 0,104 м проти 0,147 м у `phased_side_guard`. У SITL на протоколі кроку 7 (10 польотів) 9/10 побітово однакові з `phased_side_guard`; у єдиному польоті з FAILED (`room180_p3`) 3 повтори без виходу, далі утримання, FAILED 26% → 20%, зазор не гірший |
| **`phased_side_guard`** (порівняння; кандидат holdout) | Мережа летить, доки ToF не покаже перешкоду ближче 0,85 м. Тоді фаза **гальмування**, далі **поворот**, доки фронт не стане вільним (≥ 1,05 м). На відкладеному наборі 6/6 без контакту й без зазору < 0,10 м, на робочому наборі контакт у 1/20 прогонів і зазор < 0,10 м у 4/20. У SITL у кімнаті зазор < 0,10 м у 5/5. Частина цієї безпеки походить зі стагнації: застряглий дрон не врізається, бо стоїть. Чи дає мережа щось понад самі правила, перевіряє контрольний дослід «тупа політика» у [звіті](../docs/REITERATION_REPORT_UK.md) | Частку керування забирають правила: на відкладеному наборі `network_share` < 0,80 у 6/6 (у розділених кімнатах лише 0,11). **Застрягає:** у кімнаті з перегородками (`divided`) поворот не знаходить вільного фронту за таймаут, і координатор 84% часу стоїть у фазі **FAILED**, утримуючи дрон. У SITL та сама фаза з'явилася в одному з п'яти польотів у кімнаті (26% часу) |
| **`pipeline_v1`** (порівняння) | Мережа керує найбільше: `network_share` ≥ 0,80 у 19/20 прогонів робочого набору й 6/6 на відкладеному. Індикатор здебільшого показує «Мережа» | **Ризикований.** ToF бачить лише 45° уперед, а бічна сліпа зона широка. Мережа відвертає від перешкоди приблизно на 0,7 м, перешкода зникає з поля зору, і через 8–20 с дрон повертається до неї наосліп. Контакт у 7/20 прогонів робочого набору й 3/6 на відкладеному, зазор < 0,10 м майже скрізь |
| **`pipeline_v1_r7`** (доступний, не основний) | Пам'ять загроз, утримання швидкості й перевірка «точки пам'яті проти шляху корпусу». На мапі видно точки пам'яті | Менше контактів (3/20), але й частка мережі низька (4/20). Перед перешкодою позаду може надовго застрягти: мережа просить «назад», а відступ заборонено |

Історичні профілі (попередній MVP, контроль A, фазовий v2, гальмування) лишаються у списку для відтворення старих записів.

### Сцени для показу

Усі — **«Кімната 8×8 · перешкоди»**, щільність 20%, старт X −0,7, Y 0, напрям 0°, **Тривалість 60 с**. Змінюються лише **Seed** і **Розподіл** у Налаштуваннях сцени. Числа отримано однократними прогонами (`evaluate/demo_seed_search.py`, 20 seed × 2 розподіли × 2 профілі, `output/pipeline_v1_step8/seed_search.json`) і перевірено через сервер демо. Числа в таблиці отримано до кроку 9, для `phased_side_guard` і `pipeline_v1`; новий основний профіль `phased_failed_exit` у них не літав.

**Відтворюваність seed залежить від моменту ввімкнення AUTO.** Standalone детермінований, але до AUTO дрон зависає, і стан фізики, сенсорів і мережі на момент AUTO залежить від того, скільки він уже провисів. Тому той самий seed дає той самий політ лише за однакового старту: залиште **«Автономне»** і натисніть **«Старт»**, тоді AUTO запитується одразу. Якщо стартувати в ручному режимі й увімкнути AUTO пізніше, траєкторія буде іншою. Наприклад, seed 3934218795 зі скупченням з AUTO одразу не застрягає, а з AUTO на 6-й секунді застрягає у FAILED.

| Що показати | Seed | Розподіл | `phased_side_guard` | `pipeline_v1` |
|---|---|---|---|---|
| **(а) Порівняння профілів** | **20261023** | Рівномірно | 60 с без контакту, мін. зазор 0,203 м, частка мережі 0,72 | частка мережі 0,95, **контакт із коробкою на 26,2 с** |
| (а′) те саме для «Скупчення» | 20261032 | Скупчення та просвіти | без контакту, 0,209 м, частка 0,78 | частка 0,89, контакт із коробкою |
| **(б) Застрягання `phased_side_guard`** | **20261025** | Скупчення та просвіти | **фаза FAILED 60% часу**, частка мережі 0,31, без контакту (0,117 м): дрон стоїть після таймауту повороту | без контакту (0,047 м), частка 0,82 |
| (б′) те саме для «Рівномірно» | 20261040 | Рівномірно | FAILED 62%, частка 0,25 | без контакту, частка 0,94 |

**У SITL (`phased_side_guard`, 60 с; числа отримано до кроку 9, тепер SITL-демо літає з `phased_failed_exit`):**
- seed **20261023 / Рівномірно** — без контакту, частка 0,66, але мінімальний зазор 0,069 м. Маршрут у SITL розходиться зі Standalone, як і в кроці 7.
- seed **20261025 / Скупчення** — застрягання відтворюється: FAILED 60% часу, частка 0,30, без контакту.

Це ілюстрації, а не оцінка: висновки ітерації спираються на розкид і holdout у [зведеному звіті](../docs/REITERATION_REPORT_UK.md).

## Додатково: Standalone докладно

Відкрити **http://127.0.0.1:8765/** у сучасному desktop-браузері.
Вкладка **«Наживо»** → керування **«Автономне»** → **«Старт»**.
WASD не потрібні: свіжа сцена запускає pinned мережу, запитує AUTO через
чинний admission, далі прийняті команди керують фізикою. Панель МУХИ
показує 306 реальних станів `h` та команди до/після координатора.
Жива сцена за замовчуванням — кімната 8×8 м зі щільністю перешкод 20%.
Щільність 0–35% означає частку площі підлоги під випадковими перешкодами;
кількість визначається автоматично, обмеження 18 об'єктів у панелі немає.
Доступні «Скупчення та просвіти» й «Рівномірно», блоки, колони та перегородки
різних розмірів. Панель показує фактичні відсоток і кількість у створеній сцені.
Можна змінити щільність/seed, створити іншу розстановку або додати
стіну з центром X/Y, довжиною та напрямом 0°/90°. Геометрія застосовується
тільки до нового прогону. M — MANUAL одразу; Enter — запит AUTO після admission.
Готові прогони — у вкладці **«Записи»**. Вибір запису одразу відкриває його.
Налаштування сцени, докладні сенсори, графіки та події згорнуті за замовчуванням.
**«Зберегти запис»** розташовано у верхньому рядку відразу біля кнопки старту.
Камера й масштаб огляду обираються у двох списках над сценою.
Пауза відкликає AUTO через чинний приймач. **«Новий старт»** створює нову
сесію, якщо AUTO вже відкликано; ручну паузу можна продовжити.
Тривалість живої сцени — **1–600 секунд**, за замовчуванням 180 с. Її можна
редагувати під час польоту; новий ліміт має перевищувати час, що вже минув.
Зміни ліміту записуються у input schedule та точно відтворюються.
**«Межа контакту»** показує фізичну межу живого дрона (R = 0,20 м).
Діаметр — 40 см, мінімальний проміжок нової генерації — 48 см.
Старі записи відтворюються зі своїм записаним радіусом (10 см).
Видимі корпус і пропелери вкладаються в неї; перший контакт завершує прогін.
Нові живі прогони використовують точну перевірку сфери на всьому фізичному
кроці: біля кутів боксів і країв циліндрів зайва прямокутна зона не зупиняє дрон.
Версія перевірки записується як `contact_model: sphere-sweep-v1`.
Наближення для огляду — колесом над сценою.
Якщо сервер уже був запущений до оновлення коду, його слід перезапустити.
Потрібне вже встановлене середовище проєкту; нових Python/JS залежностей немає.
Сервер слухає тільки `127.0.0.1`. Зупинка — Ctrl+C у вікні запуску.

Повна [інструкція для захисту, формат запису та перевірки](../docs/INTERACTIVE_DEMO_UK.md).
Окреме [питання чинного контракту відкликання](../docs/INTERACTIVE_DEMO_CONTRACT_NOTES_UK.md).
Підсумкові hashes та evidence: [verification.json](verification.json).

Записи у `recordings/` працюють без інтернету. UI assets — у `web/`, без CDN.
Параметр `--port 8766` дозволяє використати інший локальний порт.

```powershell
.\venv\Scripts\python.exe -m demo --verify-examples
.\venv\Scripts\python.exe -m demo --verify-recording demo/recordings/03_auto_stop_takeover.json.gz
```

`--record-examples` створює записи лише за відсутності відповідних файлів
(exclusive create). Не перезаписує перевірені артефакти мовчки.
